# Implementation Plan: RLS and Security

**Branch**: `006-rls-and-security` | **Date**: 2026-06-28 | **Spec**: `specs/006-rls-and-security/spec.md`

**Input**: Feature specification from `/specs/006-rls-and-security/spec.md`

## Summary

Refine existing coarse RLS policies on all 9 reservation tables to enforce granular role-permission mapping across 3 roles (admin, front_desk, accountant). Add column-level security for pricing and sensitive fields, terminal-state protection for checked_out/cancelled/no_show reservations, RPC-level permission checks, and application-level audit logging for all reservation mutations.

## Technical Context

**Language/Version**: SQL (PostgreSQL 15+ via Supabase)

**Primary Dependencies**: Supabase/PostgreSQL, existing `can_read_reservations()`/`can_write_reservations()`/`can_override_pricing()` helper functions, existing `current_app_role()` helper, existing `audit_logs` table and `log_action` enum

**Storage**: PostgreSQL — all 9 existing reservation tables (no new tables)

**Testing**: Manual SQL test scripts via `psql` or Supabase SQL editor verifying RLS allow/deny per role × operation × state

**Target Platform**: Supabase managed Postgres (production + local dev)

**Project Type**: Database-security migration (pure SQL, no application code changes)

**Performance Goals**: RLS policy evaluation overhead should not add more than 5ms per query (defense-in-depth — API layer is primary auth)

**Constraints**: Must not break existing API service calls; all new policies must fail closed (deny by default); existing `can_read`/`can_write` helper signatures preserved for backward compatibility

**Scale/Scope**: 9 tables, 3 roles, ~35-40 individual policies, 2 new helper functions, 0 new tables
